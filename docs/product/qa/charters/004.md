# Charter 004: daemon and control socket (T030)

Session: 2026-10-24, about 40 minutes. Tester: builder (charter track, wave 6). Code under test: `dev` at 6308b65.

## Mission

*Explore* the daemon and its control socket *with* malformed and huge lines, many connections, slow readers, pause and timed pause across restarts, wall-clock jumps and store errors *to discover* invariant violations: the daemon must stay responsive, must not lose its pause state, and must keep time correctly.

## Setup

- The real binary in the tools image with temp XDG dirs, with no display (backend `none`) or with a private Xvfb.
- Socket clients are `socat` and a Python driver.
- Clock jumps come from an `LD_PRELOAD` shim, built in the container from the scratchpad, that adds an offset to `CLOCK_REALTIME` only. A suspend looks the same to the process: wall time jumps and `CLOCK_MONOTONIC` does not move.
- Synthetic text only.

## What I tried

1. **Malformed lines.** 24 of them:
   - `{`, `null`, `[]`, a bare string, a missing id;
   - `v: 2`;
   - ids that are negative, `1e400`, a string, or 2⁶⁴;
   - `limit` set to -1 or 1e9;
   - `for` set to `0s`, `86401s`, `24h`, `1440m`, or a 20-digit number of hours;
   - empty, negative and huge refs;
   - an unknown event, a non-bool `all`, a NUL inside `op`, duplicate `op` keys.
   Also invalid UTF-8, 100 000-deep nesting, CRLF, and EOF without a newline.
2. **Line limits.** Exactly 2 MiB, 2 MiB + 1, and 64 MiB without a newline.
3. **Connections.**
   - 300 idle connections, then status from a new one.
   - 100 concurrent clients × 20 `list`.
   - A slow reader that pipelines requests and never reads, with another client asking meanwhile.
   - A subscriber that never reads, while 3 000 pause/resume toggles fire events.
   - SIGTERM while clients are stuck.
4. **Pause across restart.**
   - An indefinite pause across SIGTERM.
   - `pause --for 3s`, then SIGKILL, then a restart after the deadline.
   - `pause --for 1h` across SIGTERM.
   - All with no backend and with Xvfb.
5. **Clock jumps.**
   - Wall +10 h while the daemon runs.
   - A timed 60 s pause, then wall +1 h.
   - Wall −2 days, then a restart.
   - Wall +8 days while running, then a restart.
6. **Store errors.** Full disk, a corrupt index and unreadable content (details in charter 001).

## Observations

- **Malformed input.** Every malformed input got a well-formed `bad_request` (or `unsupported_version` with the request's id). The daemon stayed up.
- **Duplicate keys.** Duplicate `op` keys take the last value: `{"op":"status",…,"op":"clear"}` ran `clear`.
- **Line limits.** 2 MiB exactly was answered, and the connection stayed usable. 2 MiB + 1 got `too_large` (id 0), then the connection closed. A 64 MiB line was cut off at the limit (broken pipe on the sender), with memory bounded.
- **Connections.**
  - The 257th connection while 256 are idle was reset without a reply. Idle connections never time out.
  - With 256 idle connections held, `rstory status`, `ls` and `pause` print `unexpected answer from the daemon: the connection closed` and exit 1. `ls` does not fall back to the read-only store.
  - 100×20 concurrent `list`: no errors, p50 5.6 ms, p99 7.2 ms.
  - A slow reader stuck after 387 pipelined requests did not affect another client (1 ms).
  - A stuck subscriber plus 3 000 events: 0.75 s, no effect.
  - SIGTERM with stuck clients exits within about 200 ms and removes the socket. RSS was 19 MB, with 15 fds.
- **Restarts.**
  - A stale socket after SIGKILL is replaced on start.
  - A second daemon says `already running (pid N)` and exits 4.
  - An indefinite pause and a `--for 1h` pause both survive SIGTERM and SIGKILL restarts.
  - A timed pause whose deadline passed while the daemon was down comes back as `recording`, but see D2.
- **Inactive hides pause.** While inactive (no backend), `status` shows `inactive` with `paused_until: null` even when a 1 h pause is persisted.
- **Clock.** The daemon's clock is the wall time at start plus `Instant::elapsed()`; see `Clock` in `src/daemon/state.rs`.
  - After wall +10 h, new entries were stamped at the old time.
  - A 60 s timed pause did not end after wall +1 h, and the client saw `paused_until` an hour in the past.
  - After wall −2 days and a restart, new entries are clamped to the newest stored `last_copied`, so the order is preserved.
  - A restart at +8 days expired the whole unpinned history, as TTL rules say.

## Findings (by severity)

### D1 Medium: the daemon clock ignores wall-clock changes, and by Linux semantics also ignores suspend

`Clock::now()` is `wall_at_start + Instant::elapsed()`. On Linux, `Instant` is `CLOCK_MONOTONIC`, which does not advance during suspend. After a laptop sleeps overnight (10 h), and with the shim reproducing that:

1. New entries get `created`/`last_copied` 10 h in the past, so `ls`, the picker and the extension show wrong ages ("10 h ago" for something just copied).
2. A timed pause's `paused_until` reads as the past to every client. The extension's countdown disappears while the daemon still says `paused`.
3. TTL expiry drifts by the cumulative suspend time. After a restart (real wall time), entries stamped "too old" can expire days earlier than 7 days after their real copy.
4. A daemon started before NTP corrected the RTC (dual-boot local-time RTC) keeps the wrong offset until restart.

**Repro (container):**
1. `cc -shared -fPIC -o /tmp/shim.so shim.c -ldl` (adds `/tmp/clockoff` seconds to `CLOCK_REALTIME`).
2. Start the daemon with `LD_PRELOAD=/tmp/shim.so`, then copy.
3. `echo 36000 > /tmp/clockoff`, then copy again.
4. The second `last_copied` equals the first plus about 0.4 s, not +10 h.

**Fix direction:** read `OffsetDateTime::now_utc()` on each `now()`, clamped to be non-decreasing against the newest stored time (the clamp already exists), and recompute timers on every wakeup.

**Assertion to add** (unit test in `src/daemon/state.rs`, with an injectable wall source): after the wall source advances by 10 h with no monotonic time passing, `clock.now() - before >= 10h`.

### D2 Medium: a timed pause that expires while the daemon is down leaks the copy made during the pause

**Repro (Xvfb):**
1. `rstory pause --for 1s`.
2. `printf synthetic-held | xclip -selection clipboard -i -loops 1 &` (the owner stays alive).
3. Stop the daemon (TERM or KILL) and wait 1.2 s.
4. Start the daemon. `rstory ls` now lists `synthetic-held`.

The same copy is correctly skipped when the pause ends in a running daemon, and when the daemon restarts while still paused. Only the start-up capture of the current selection bypasses the user's pause. This is the privacy charter's pause gate; see charter 005, P1.

**Fix direction:** when `RecordingState::load` reports that a stored pause just ended (`changed == true`), treat the selection present at start as seen and do not read it.

**Assertion to add** (e2e or a daemon process test): after the steps above, `assert!(!ls.contains("synthetic-held"))`.

### D3 Low: idle connections never time out, and slot exhaustion looks like a broken daemon

**Repro:** hold 256 connections open (Python), then run `rstory status`. It prints `unexpected answer from the daemon: the connection closed` and exits 1, and `rstory ls` doesn't fall back.

Only a same-uid process can do this, so the security impact is nil. Still, a leaking client (an extension bug) would make every other client fail confusingly. Suggestion: an idle timeout for connections without a subscription, plus a clearer CLI message.

### D4 Low: `status` hides a persisted pause while inactive

**Repro:** with no display, run `rstory pause --for 1h`, then `rstory status --json`. It shows `{"state":"inactive","paused_until":null}`.

When the backend returns, the daemon is paused, but no client could tell beforehand. Suggestion: keep `paused_until` (or a `paused: true`) in the inactive view.

### D5 Info

- JSON duplicate keys take the last value (the contract is silent).
- The +8-day restart wiping unpinned history is correct TTL behaviour, but it is unguarded against a wrong RTC.

## Open questions

- Should a dedicated `store_error` code replace `internal` for disk-full failures (charter 001, S2)?
