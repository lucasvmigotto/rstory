# Charter 001: store and history (T028)

Session: 2026-10-24, about 40 minutes. Tester: builder (charter track, wave 6). Code under test: `dev` at 6308b65.

## Mission

*Explore* the store and history *with* SIGKILL during copy bursts, torn writes, a full disk, permission drift and a concurrent read-only client *to discover* invariant violations: the store must open after any crash, the caps must hold, and nothing may be half-visible.

## Setup

- The real debug binary built in the tools image (`make TARGET_VOLUME=rstory-tools-target-charters build`), run with a cleared environment and temporary `XDG_RUNTIME_DIR`, `XDG_STATE_HOME`, `XDG_CONFIG_HOME` and `HOME`.
- A private Xvfb in the container. Copies come from `xclip -loops 1` with synthetic text only.
- For a full disk, the store sits on a size-limited tmpfs (`--tmpfs /small:size=600k|1500k`).
- The probe scripts live in the session scratchpad, not in the repo. They are a Python SIGKILL driver, shell scenarios, and an invariant checker that reads `index.json` and `content/` directly.

## What I tried

1. **SIGKILL during bursts.** Each cycle starts the daemon, starts a burst of xclip copies (10 B to 1 MiB + 1, 0 to 50 ms apart), sends SIGKILL at a random moment between 0.05 and 1.5 s, and restarts the daemon. After each restart the checker verifies: `len ≤ max_entries`, unique ids and hashes, every row has a content file of the recorded size, no orphan content files, no `index.json.tmp`, `last_copied` descending, every mode 0700/0600. A final `show` runs on every entry.
   - Run A: 60 cycles with mixed sizes, 1 968 copies.
   - Run B: 150 cycles with 0.5 to 1 MiB copies only, 14 107 copies.
2. **Torn writes**, made by hand while the daemon was down:
   - a truncated content file;
   - a same-size content file with different bytes;
   - stray `.tmp-*` and `index.json.tmp` files;
   - a foreign file in `content/`;
   - a half-written `index.json`, an empty one, one with `version: 2`;
   - an index with more pins than `max_pinned`.
3. **Full disk.** Large copies until the tmpfs filled. Then copies, `pause`, `pin`, `rm`, `clear` and `copy` on a completely full disk, a restart on a full disk, and recovery after freeing space.
4. **Permission drift.**
   - `chmod 644` on a content file while the daemon runs, then a restart.
   - `chmod 000` on a content file, then `show` and `copy`.
   - The store dir at 0755, `store.lock` at 0666.
   - The store dir as a symlink into a 0755 parent.
5. **Concurrent read-only client.**
   - `rstory pick` held open in a pty while the daemon starts.
   - 600 back-to-back `rstory ls` during daemon start.
   - `flock -s store.lock` held for 5 s, standing in for a slow reader.

## Observations

- **Crash safety held.** 210 SIGKILL cycles, 16 075 copies, 5 recovery sweeps logged (`store recovery sweep orphan_files=… dropped_rows=…`), zero invariant violations and zero start failures. A burst of 400 copies kept exactly 20 entries with `dropped_burst = 0`. No synthetic text appeared in any log.
- **Torn content is handled by size.** A truncated file is hidden by the read-only view and swept by the daemon (row dropped, file unlinked). Stray `.tmp-*` files are removed; foreign files are left alone. A same-size file with different bytes is not detected: the row's BLAKE3 hash is never checked on read, sweep or restore.
- **A corrupt `index.json` stops everything.** The CLI says `Cannot read the store: index.json is corrupt at line 1, column 100` and exits 5. The daemon says `could not open the store (corrupt)` and exits 1. Doctor shows `✗ Store cannot read the store in …` with no hint. Nothing tells the user how to recover.
- **Full disk.**
  - A copy whose commit fails is lost silently. The only trace is `ERROR … capture commit failed kind=io`. `status` still says `recording` with no counter, and doctor reports `✓ Store private (0700/0600), 4 entries`.
  - Once space is freed, recording resumes and the index is intact.
  - On a completely full disk, `pause`, `pin`, `rm`, `clear` and `copy` all fail with `internal error (see the daemon log, cN)` and exit 1. The log only says `store error kind=io`.
  - `pause` is therefore refused, so recording goes on (see charter 005).
  - `copy` takes clipboard ownership before the failed commit, so the CLI reports an error although the clipboard did change.
- **Permissions.**
  - A drift while the daemon runs is not noticed: the daemon keeps writing, and doctor flags it with `✗ Store permissions are too open`.
  - The next start is refused with exit 5 and a message naming the path.
  - Any group- or other-readable file in the store also blocks the start (exit 5): a stray 0644 `index.json.tmp`, or a foreign `content/not-ours.txt`. The sweep would delete the first and deliberately leave the second.
  - A symlinked store dir in a 0755 parent is accepted, because only the store dir itself is checked.
  - An unreadable content file makes `show` and `copy` fail with `internal` (the log has the correlation id).
- **Lowered caps.** With `max_pinned = 1` and 3 pinned rows, the daemon starts and keeps all 3 pins (`pinned 3 > max_pinned 1`). That matches `pins_over_cap` being informational, but it is not documented in the CLI.
- **Read-only clients.**
  - The picker does not hold `store.lock` while open, so the daemon started fine.
  - 600 back-to-back `ls` runs did not block the start.
  - A reader holding `LOCK_SH` for more than 2 s makes the daemon give up with `a client is reading the store; retry` and exit 5. An XDG-autostarted daemon would not retry.

## Findings (by severity)

### S1 Medium: capture commit failures are silent to the user

**Repro:**
1. Put `XDG_STATE_HOME` on a 1.5 MB tmpfs.
2. Copy four 400 kB texts.
3. The fourth is missing from `rstory ls`.
4. `rstory status --json` shows `recording` and no counter.
5. `rstory doctor` shows `✓ Store`.

The daemon log only has `capture commit failed kind=io`, and the `io::ErrorKind` (StorageFull) is dropped by `error_kind()`.

**Expected:** some user-visible signal (a status reason, a doctor warning, or at least the error kind in the log).

**Small part I'd fix now:** log the `io::ErrorKind`. Assertion to add (tests/store_fail.rs style, FaultFs ENOSPC on commit, `tracing` capture):
`assert!(log.contains("capture commit failed") && log.contains("StorageFull"));`

The status or doctor signal is a product decision (Doubts).

### S2 Low: generic `internal` for store errors on control ops

**Repro:** on a 100 % full store tmpfs, run `rstory pause`, `pin 0`, `rm 1`, `clear --yes` and `copy 0`. Each prints `internal error (see the daemon log, cN)` and exits 1.

`copy` has already served the entry, so the clipboard changed although the CLI reported failure. This should be a dedicated code, or at least `copy` should succeed when only the "move to top" commit failed.

### S3 Low: no recovery path for a corrupt index

**Repro:** with the daemon down, run `head -c 100 index.json > index.json.new && mv index.json.new index.json`. Then:
- `rstory ls` exits 5;
- `rstory daemon` exits 1 (an unexpected error, while the CLI calls the same condition an environment error);
- doctor gives no hint.

Our own writes are atomic, so this needs external damage or filesystem corruption. When it happens, the history is unusable until the user finds and moves the file. Suggestion: name the file and suggest moving it aside, or quarantine it as `index.json.corrupt-<ts>` and start empty.

### S4 Low: a foreign or stale file with group/other bits blocks the daemon

**Repro:**
1. `umask 022; touch $STORE/content/notes.txt` (or a stale `index.json.tmp` at 0644).
2. `rstory daemon` exits 5 with `store is too open: …/content/notes.txt`.

The policy is strict by design, but the sweep would remove the tmp file anyway, and the foreign file is "not ours". Question: should the permission check skip files the store does not own?

### S5 Low: a long-lived read-only reader makes the daemon give up after 2 s

**Repro:**
1. `flock -s $STORE/store.lock sleep 5 &`
2. `rstory daemon` exits 5 with `a client is reading the store; retry`.

No shipped reader holds the lock that long (the picker releases it), so this is a robustness note for autostart. A longer retry, or a retry loop in the autostart unit, would cover it.

### S6 Info

- Same-size corruption is not detected: `hash` is never verified on read or restore.
- Pins above a lowered `max_pinned` are kept.
- A symlinked store dir with a world-readable parent is accepted.

## Open questions

- Should `status` and doctor surface "the last capture could not be saved" (S1)? It needs a protocol field or a doctor probe, which is a contract change.
- Should restore verify the content hash before serving (S6)?
- Is the permission check meant to cover foreign files in the store (S4)?
