# Charter 002: X11 capture and the XWayland bridge (T024)

Session: 2026-10-24, about 35 minutes. Tester: builder (charter track, wave 6). Code under test: `dev` at 6308b65.

## Mission

*Explore* X11 capture, including the XWayland bridge, *with* INCR transfers, odd and hostile owners, owners that exit, XWayland loss on headless mutter and display loss *to discover* invariant violations: no partial entries, the size cap never truncated, and the daemon stays responsive.

## Setup

- The real binary in the tools image with temp XDG dirs and a private Xvfb, or headless mutter with XWayland via `tests/support/mutter.rs`.
- For owners that xclip can't produce, an ad-hoc probe test ran in a scratch copy of the repo, outside the worktree. It reuses `tests/support/x11.rs` with two probe-only knobs on `Offer`: `chunk_delay` (sleep before each INCR chunk) and `die_after_chunks`. The daemon under test is always the real `rstory daemon` process, and the CLI measures its responsiveness.
- Synthetic text only.

## What I tried

1. **Slow INCR.** 64 KiB in 1 KiB chunks with 1.5 s between chunks, while running `rstory status` four times.
2. **Owner dies mid-INCR.** 300 KiB in 4 KiB chunks, connection closed after 5 chunks, then a normal copy.
3. **Stalled owners.** Ten owners that answer TARGETS but never the data, taking the selection 30 ms apart, then a normal copy.
4. **Odd owners:**
   - STRING (Latin-1) only;
   - `text/plain;charset=utf-8` only;
   - `TEXT` only;
   - an owner that refuses every conversion;
   - invalid UTF-8 in UTF8_STRING;
   - NUL bytes;
   - whitespace only;
   - exactly 1 MiB via INCR, 1 MiB + 1 via INCR, 1 MiB + 1 in one property;
   - sensitive-hint variants (see charter 005).
5. **Display loss.** Kill Xvfb with the daemon running, then start a new Xvfb on the same display number.
6. **Bridge.** Capture via XWayland on headless mutter, then `pkill -KILL Xwayland` during a slow INCR, sampling `status` every second.
7. **Restore during churn.** 60 `rstory copy 5` while 150 xclip copies run 20 ms apart. Then 20 back-to-back restores and read-back with `xclip -o`.

## Observations

- **Slow INCR wedges the daemon.** Every `status` took 2.0 s and failed with `The daemon did not answer in time. Run rstory doctor for details.` (exit 1) for the whole transfer. In `src/backend/x11/incr.rs`, `incr_new_value` resets `deadline = now + read_timeout` on every chunk, and there is no total deadline. `process_queue` awaits `read_text` on the daemon's single event loop, so socket requests, restores and timers all wait.
- **Owner death mid-INCR is handled.** The read times out, `status` answers in 4 ms, and the next copy is recorded.
- **Stalled owners coalesce.** Only the first `status` waited about 2 s (one read timeout). The others answered in about 2 ms, and the next normal copy was recorded right away.
- **Odd owners:**
  - Latin-1 is converted (`synthetic-latin1-é`), and `text/plain;charset=utf-8` is read.
  - A `TEXT`-only owner is ignored (no entry, no counter).
  - A refusing owner gives no entry and no counter.
  - Invalid UTF-8 is stored with replacement characters; NUL is kept and escaped in the preview.
  - Whitespace-only text (`" \n\t "`) is recorded. The spec ignores only empty text.
- **Size boundaries hold.** Exactly 1 MiB is recorded. 1 MiB + 1 is skipped whole (`skipped_oversize` +1) through both INCR and a single property.
- **Display loss.** The daemon goes `inactive` (backend none), then reconnects to a new Xvfb on the same display and records again.
- **Bridge.** Killing XWayland also ended headless mutter, as it would end a GNOME session. The daemon went `inactive (disconnected)`. During the following seconds, `status` alternated between "did not answer in time" and `inactive`: `maybe_reconnect` awaits the bridge connector inline, and that connector retries for up to `connect_timeout` (3 s). The daemon keeps retrying forever after its session is gone.
- **Restore during churn.** All 60 restores succeeded, with no duplicate entries and `dropped_burst = 0`. Read-back matches.

## Findings (by severity)

### X1 Medium: a slow INCR owner blocks the daemon for the length of the transfer, with no upper bound

**Repro (probe test):**
1. Start an Owner with `incr_threshold = 1024`, `chunk_delay = 1.5 s` and 64 KiB of text.
2. Run `rstory status` repeatedly: every call fails after 2 s for about 96 s.
3. With 1-byte chunks every 1.9 s, the wedge lasts days.

Any X client (or a legitimately slow one, such as an app over `ssh -X`) can make the CLI, the picker, the tray and the extension unresponsive and block restores.

**Small fix:** an overall read deadline set once at `begin_incr` (or in `start_read`), for example 5 s or a size-based budget. The per-chunk idle deadline would stay.

**Failing assertion to add** to `tests/x11_capture.rs`, using a `chunk_delay` knob on the support `Offer`:
```rust
let t = Instant::now();
let r = b.read_text(2 * MIB).await;
assert!(matches!(r, Err(ReadError::Timeout)) && t.elapsed() < Duration::from_secs(6));
```
That uses an owner sending 1 KiB chunks every 1.5 s for 64 KiB.

### X2 Low: in bridge mode the reconnect loop blocks the event loop

**Repro:**
1. Run the daemon in bridge mode on headless mutter.
2. Run `pkill -KILL Xwayland`.
3. Run `rstory status` once a second: about half the calls time out.

The bridge connector retries for up to 3 s inside `maybe_reconnect`, which runs on the event loop. Suggestion: one connect attempt per timer tick (the daemon's own backoff already spaces them), or a connect off the loop.

### X3 Info

- `TEXT`-only owners are ignored.
- Whitespace-only text is recorded (see the open questions).
- The daemon keeps retrying after its session ended (mutter gone).

## Open questions

- Should whitespace-only text count as "empty" (spec 005 says "an empty text is ignored")?
- When the session the daemon was started for is gone (the compositor died with XWayland), should the daemon exit so autostart or systemd can start a fresh one, instead of retrying forever?
- "Restore into Wayland apps" through the bridge can't be checked headless. The owner's manual rows in `docs/release.md` cover it.
