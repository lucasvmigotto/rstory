# Charter 013: release and publishing

Session: 2026-10-24, about 30 minutes. Tester: builder (charter track, wave 6). Code under test: `dev` at 6308b65. Since then, `dev` (PRs #77 to #79) changed `ci.yml` (perf smoke) and `nightly.yml`, but not `release.yml` or the tools action. The findings below still apply.

## Mission

*Explore* release and publishing *with* an adversarial reading of the workflows (injection, permissions, the tag and branch guard, cache poisoning, the SC-001 token assertion), plus `make publish-dry-run`, *to discover* ways to publish something unintended or leak the publishing credential. The `qa.md` charter adds: a tag on a non-main commit, a version mismatch, an arm64 runner that is unavailable.

## Setup

- I read `.github/workflows/{release,ci,nightly}.yml`, `.github/actions/tools/action.yml`, `.github/scripts/no-publish-token.sh`, `.github/dependabot.yml`, `Containerfile`, `Makefile` and `docs/release.md` ("Owner setup", "Pipelines").
- I ran `make TARGET_VOLUME=rstory-tools-target-charters publish-dry-run` (networked, as the recipe says) and `cargo package --list` (offline).

## What I tried

1. **Injection.** For every `run:` block, I checked whether untrusted values (`github.ref_name`, `github.workflow`, inputs) are inlined into the script or passed through `env:`.
2. **Permissions.** I checked the per-job `permissions`, which jobs get `id-token: write` and `contents: write`, which jobs run in the `release` environment, and the reusable `ci` call's `issues: write`.
3. **Tag and branch guard.** I traced:
   - a tag on a dev-only commit;
   - a tag on an old main commit;
   - `v1.2.3`, `1.2.3-rc.1`, and a tag different from `Cargo.toml`;
   - `workflow_dispatch` with `dry_run: false` and from another branch.
4. **Cache poisoning.** I looked for every `actions/cache`/restore path, and for what the tools image is built from.
5. **The SC-001 assertion.** I looked for patterns that would pass a stored token without matching the script.
6. **Publishing.** I traced what runs while `CARGO_REGISTRY_TOKEN` is set.
7. **`make publish-dry-run`** and the package contents.

## Observations

- **Injection.** All untrusted values reach scripts through `env:`; none are inlined. The tag trigger glob (`[0-9]+.[0-9]+.[0-9]+`) plus the regex in `verify` restrict `ref_name`. No `pull_request_target` anywhere, and `persist-credentials: false` on every checkout.
- **Permissions.**
  - Top-level `permissions: {}`.
  - `id-token: write` only in `publish`, which is also the only job in the `release` environment.
  - `contents: write` only in `github-release`.
  - The reusable `ci` call grants `issues: write`, but `ci.yml`'s reporter only runs on `refs/heads/` pushes, so it is skipped on tags.
- **Guard.**
  - `verify` refuses a non-`X.Y.Z` tag, a mismatch with `Cargo.toml`, and a commit that is not an ancestor of `origin/main`.
  - A tag on an *old* main commit passes the ancestor check, but would also need the old `Cargo.toml` to carry the new version, so it's harmless.
  - A manual run with `dry_run: false` fails in `verify`. Manual runs never set `publish=true`.
- **arm64.** `ubuntu-24.04-arm` is available because the repo is public. If it isn't, `build (aarch64)` queues until GitHub's 24 h limit, then fails; `publish` needs `checksums`, so nothing is published. It fails closed.
- **Caches.** There is no `actions/cache` in any workflow; the tools image is rebuilt per job. The base image is pinned by digest, and every downloaded tool is checked by `sha256sum -c`. Every action is pinned by full SHA, and Dependabot keeps the pins current with a 14-day cooldown. I found no cache-poisoning surface.
- **SC-001 script.** It matches `secrets\.[A-Za-z_]`, `secrets\[`, and `CARGO_REGISTRY_TOKEN` lines that lack `steps.auth.outputs.token`. It does not catch:
  - `secrets: inherit`;
  - `toJSON(secrets)` (no dot after `secrets`);
  - `vars.*`;
  - the alternative variable `CARGO_REGISTRIES_CRATES_IO_TOKEN`;
  - a forbidden reference followed by `# steps.auth.outputs.token` on the same line, when it doesn't use `secrets.`.
- **Publish.** `make publish` runs `cargo publish --locked` in the networked tools container with `CARGO_REGISTRY_TOKEN` in its environment. `cargo publish` verifies by building the packaged crate, so every dependency's build script and proc macro runs with the token in its environment and network access. The token is short-lived (the auth action revokes it at job end) and scoped to this crate, but it is a live crates.io credential.
- **Dry run.** `make publish-dry-run` is green (16 s with a warm cache). It packaged 623 files (2.2 MiB, 611.5 KiB compressed), verify-built the package, and stopped at "aborting upload due to dry run".
  - The package includes `specs/` (156 files), `docs/` (16), `tests/` (98), the Makefile, the Containerfile and deny.toml.
  - `.github/` and untracked files are not in it.

## Findings (by severity)

### R1 Medium: the crates.io token is present while third-party build code runs

**Where:** the `publish` job, `make publish`, then `cargo publish --locked` with verification.

A compromised dependency's `build.rs` or proc macro runs inside the publish verification with `CARGO_REGISTRY_TOKEN` set and network on. It could publish a malicious version of `rstory` within the token's lifetime.

**Fix direction:** in the publish job only, `cargo publish --locked --no-verify`. The `publish-dry-run` job already verified the same commit, and `publish` needs it. Alternatively, run the verification build before the OIDC exchange step.

**Check to add:** `no-publish-token.sh` (or a new step) asserts that the `publish` recipe passes `--no-verify`, e.g. `grep -q 'cargo publish --locked --no-verify' Makefile`.

### R2 Low: the SC-001 token check is bypassable

**Repro:** add `env: {ALL: ${{ toJSON(secrets) }}}`, or `secrets: inherit` on a reusable call, to any workflow. `.github/scripts/no-publish-token.sh .github` still passes.

**Assertion to add:** a fixture directory with a workflow containing `toJSON(secrets)` must make the script exit 1, and likewise for `secrets: inherit` and `CARGO_REGISTRIES_CRATES_IO_TOKEN`. The pattern would be `\bsecrets\b` outside comments, plus the second variable name.

### R3 Low: the tag ruleset is optional

`docs/release.md` lists the `*.*.*` tag ruleset as "optional". Without it, any collaborator with write access can push a release tag. The environment's required reviewer is then the only gate before publish, and `build` and `ci` still run on that tag. With a single owner today this is theoretical. Suggestion: make the tag ruleset a required setup step.

### R4 Low: the published crate carries internal planning files

623 files go out, including `specs/`, `docs/product/` (via `docs/`), `tests/`, the Containerfile and the Makefile. This is not a secret leak, but it is bulk, and the agent-orchestration and planning docs go with it. Suggestion: an `include = [...]` list in `Cargo.toml`. It must keep:
- `src/`, `build.rs` and `assets/` (the icons for `build.rs`);
- `extension/` (embedded by `include_dir!`);
- `scripts/ext-pack.py`, which `src/install/gnome.rs` `include_str!`s on `dev` since PR #79;
- LICENSE and README.

Re-run `make publish-dry-run` after the change.

### R5 Info

- The ancestor check accepts old main commits (harmless with the version check).
- An unavailable arm64 runner fails closed after 24 h.
- On a re-run, `github-release` re-uploads assets with `--clobber`. The build is reproducible, so they're the same bytes.
